# BitGigs — Agent Quick Reference

Django 6.0 app for tracking shifts and estimating Danish net pay across multiple workplaces. Bootstrap 5 + Bootstrap Icons UI, Cropper.js for icon cropping, Chart.js (CDN) for analytics charts. SQLite in dev, Postgres in prod.

## Versioning

We follow **semantic versioning — `major.minor.patch`**. The single source of truth is **`bitgigs.__version__`** in `bitgigs/__init__.py`, surfaced read-only on **Settings → About**. Bump it there as part of the commit; nothing else needs editing, and always call the bump out in the commit preview. Pure docs/comment/whitespace pushes need no bump.

- **Patch (`0.0.Z`)** — backward-compatible **bug fixes, performance and security fixes**: things that correct behaviour without changing *how the software is used*. Bump before every push that carries such a fix.
- **Minor (`0.Y.0`)** — a new, **backward-compatible feature**: functionality added without breaking existing code, data or workflows (resets patch to 0). A new feature *is* a minor bump — don't smuggle one out as a patch. For a **big implementation** (a whole new page/subsystem), still flag it and **advise the user** as you bump, so the release is a conscious one.
- **Major (`X.0.0`)** — a **breaking change**: existing integrations, stored data, the HTTP API, or older setups would fail and require the user to update to stay compatible (resets minor and patch to 0). **Never bump major on your own — discuss it first.** Separately, when it's been a long time since the last major and a lot has accumulated, open a discussion about which goals/ToDos to finish before cutting the milestone `X.0.0`.

## 🔒 HARD CONSTRAINT — data never leaves the server

**No user data or app data may ever be sent to any external/third-party service.** This is non-negotiable and applies to every feature, present and future. Any AI/LLM, embedding, search, or "assistant" capability MUST run **locally on the server** (e.g. a local inference server) — **never** an external API (no Anthropic/OpenAI/etc.). If a feature can't be done fully on-server, it doesn't ship.

**The only sanctioned outbound integrations are the two below**, and both share the same shape: optional, off unless the operator configures them, pointed at an endpoint the *operator* names, and carrying only what that feature needs. Adding a third is a deliberate decision, not an implementation detail — do not introduce one without asking.

1. **SSO/OIDC** (`OIDC_*`) — to an IdP the operator controls.
2. **SMTP** (`EmailSettings`, Settings → Email) — to a mail server the operator chooses. This one *can* be a commercial provider (Gmail, Fastmail, Microsoft 365), but that is the **operator's own decision about their own mail account**, made explicitly in the settings page, not something BitGigs does on their behalf. The app's obligation is to send only what was asked for — today a password-reset link to the operator's own address, later calendar invites. **Never** route app data (shifts, pay, workplaces) through mail without an explicit request for that feature.

## Run / verify

- Activate venv: `.venv\Scripts\Activate.ps1` (Windows PowerShell). Always use `--settings=bitgigs.settings.local` for dev.
- Smoke check after edits: `python manage.py check --settings=bitgigs.settings.local`
- Quick page render check (**must log in** — the whole site requires auth): `python manage.py shell --settings=bitgigs.settings.local -c "from django.contrib.auth.models import User; from django.test import Client; c = Client(); c.force_login(User.objects.first()); print(c.get('/PATH/').status_code)"`
- Tests: `python manage.py test apps --settings=bitgigs.settings.local` (the `apps` label is required — see layout note below). View tests need `self.client.force_login(...)` (see `LoggedInTestCase` in `apps/workplaces/tests/test_contract_overlap.py`).
- Optional `.env` at the repo root is loaded by `bitgigs/settings/base.py` (real env vars win; empty values ignored); `.env.example` documents the variables. `wsgi.py`/`asgi.py` default to **production** settings, and production refuses to boot without `DJANGO_SECRET_KEY`/`POSTGRES_PASSWORD`.
- **Databases**: dev is SQLite unless `DJANGO_DB=postgres` (env or `.env`) flips `local.py` to PostgreSQL; production is PostgreSQL always. Both build the connection from the same `POSTGRES_*` vars via `postgres_database()` in `base.py` — change connection config there, not per-settings-file.
- **Docker**: `Dockerfile` (python 3.13-slim, gunicorn + WhiteNoise, non-root, `collectstatic` at build, `docker-entrypoint.sh` migrates then serves, production settings) + `compose.yaml` (`db` = postgres:17-alpine with healthcheck + `pgdata` volume, loopback-only port; `app` on :8000 with an `instance` volume for media/setup key). The app service runs the **pre-built image** `ghcr.io/peasniped/bitgigs:latest` (overridable via `BITGIGS_IMAGE`) — no `build:` key, so `up` never builds the repo; releases are pushed **manually** (`docker build -t … && docker push …`, no CI), and a locally built tag satisfies `up` for testing unpushed changes. One `.env` drives both compose substitutions and the app. `docker compose up db` alone = local test database for host-venv dev. gunicorn is installed in the Dockerfile, **not** requirements.txt (it doesn't run on Windows). WhiteNoise middleware sits in `base.py` (inert under runserver); its compressed-static storage is set in `production.py` — deliberately **non-manifest**, so a stale static reference 404s instead of 500ing.
- **Static vs media are served by two different things, and only static is WhiteNoise's.** WhiteNoise covers `STATIC_ROOT` only; **media (`instance/media/`, i.e. uploaded workplace icons) is served by `core.views.MediaView`**, routed **unconditionally** in `bitgigs/urls.py` — not under `if settings.DEBUG`, which is what used to 404 every icon in the container. Don't hand media to WhiteNoise: it indexes files once at startup, so a *newly uploaded* icon would 404 until the process restarted. `MediaView` is deliberately **not** `login_not_required` (uploads sit behind the site login like everything else) and delegates to `django.views.static.serve`, which normalises the path and refuses to escape `MEDIA_ROOT`. `staticfiles/` is just `collectstatic` output — gitignored, dockerignored, regenerated at image build; its apparent "copies" of `assets/static/` are exactly that, plus admin/allauth's bundled assets. Tests: `apps/core/tests/test_media.py`.

## Project layout

- Feature apps live under `apps/`. `apps/` is a plain directory placed on `sys.path` (via a one-line insert in `bitgigs/settings/base.py`), **not** a Python package — so import names and app labels stay bare (`core`, `workplaces`, …) and `INSTALLED_APPS` is unchanged. Never add `apps/__init__.py`.
- Because `apps/` isn't a package, `manage.py test` with no args discovers 0 tests — always pass the `apps` label (or specific app labels).
- `bitgigs/` (project config) stays at the repo root, so `BASE_DIR` and `DJANGO_SETTINGS_MODULE`/`wsgi`/`asgi` paths are unaffected.
- Project-level assets live under `assets/`: `assets/static/{css,js,graphics}` (the staticfiles root) and `assets/templates/` (project-level templates). `graphics/` holds bundled images like the logos (referenced as `{% static 'graphics/…' %}`); user-uploaded files stay in `media/`.

## Conventions

- **Auth**: the whole site sits behind Django's `LoginRequiredMiddleware` (added in `base.py`); mark genuinely public views with `@login_not_required`. First-time setup is an **onboarding wizard** (`core.views`, URLs under `/onboarding/`, names `core:onboarding-*`). Step 1 creates the single admin account **immediately** (needed for the logged-in steps) and is only reachable while no user exists. It is **three pages**, all subclassing `_AccountStepView`: `/onboarding/account/` (the **setup key** — see below), then `/onboarding/account/method/` (the configured IdP vs email+password, shown only when `SSO_ENABLED`), then `/onboarding/account/email/` (the `OnboardingUserCreationForm`) or `/onboarding/account/sso/` (hand-off to the IdP). **Only `_AccountStepView` may define `dispatch()`** — `login_not_required` is attached to the dispatch *method*, so an overriding subclass drops the marker and `LoginRequiredMiddleware` starts bouncing anonymous visitors out of the logged-out pages; vary behaviour via its `requires_key` / `requires_sso` class attributes instead.
- **Setup key** (`core/setup_key.py`, `manage.py setup_key [--regenerate]`): a fresh install has no owner, so *whoever reaches the account step first* would claim it. The key (256-bit, `secrets.token_urlsafe`) is printed to the server log and written to `settings.SETUP_KEY_PATH` (`instance/setup_key.txt`) on first visit; the account step verifies it once, records `setup_key.SESSION_FLAG` in the session, and every later page — **including the SSO bootstrap in `core.adapters`** — refuses to act without that flag. Deleted once an owner exists. Tests must point `SETUP_KEY_PATH` at a temp file (see `SetupKeyMixin` in `apps/core/tests/test_auth.py`) or they clobber the real key. Steps Tax → Workplace → Terms are **deferred**: each step's raw POST is held in a durable per-user **`OnboardingDraft`** (`core.models`, a `OneToOne(User)` + `data` JSONField — not the session, so logging out mid-onboarding via the top-left "Log out" doesn't lose it; the `_onboarding_*`/`_store_onboarding`/`_clear_onboarding` helpers in `core.views` manage it), each payload having already passed `is_valid()` so re-binding it on revisit re-shows the input with no errors → back-navigation keeps its place. Everything is written to the DB together, atomically, only on the **Review step's** **Finish** (`core.onboarding.commit_setup`), which then deletes the draft — see the six-step bullet below. The wizard reuses the real `WorkplaceForm`/`WorkplaceContractForm`/`ContractTermSetForm` and their templates via an `onboarding=True` context flag (transient unsaved Workplace/Contract objects supply display names). **The contract has no step of its own**: its only editable field is an optional label, so the Workplace step renders `WorkplaceContractForm(prefix="contract")` alongside `WorkplaceForm` (built by `_build_contract_form`) — one raw-POST payload under the `workplace` draft key holds both, and a small script in `workplace_form.html` reveals the label field once the workplace is named. The step indicator (`core.onboarding.steps`) is 6 circles (Account / Start / Tax Profile / Workplace / Pay Terms / Review) and marks a step `done`/`active`/`started` (filled but ahead because the user went back → yellow, clickable)/`upcoming`; a step the **database** already satisfies (i.e. an import covered it) is `done` **regardless of position**, so after a full import the later circles read as finished rather than as pending work. `OnboardingRequiredMiddleware` funnels anonymous fresh installs to the account step and logged-in-but-unfinished users to `/onboarding/`; completion signal = a `TaxProfile` **and** a `ContractTermSet` exist (cached in `session["onboarding_complete"]`, also exposed to templates by `core.context_processors.onboarding_status` so `base.html` hides the nav until done and the login page shows a "finish setting up" hint). The single account is the **owner/admin**; its username **is** the email (`OnboardingUserCreationForm`, validated + copied to `User.email`) — which is why that form also **requires a display name**, stored in `User.first_name` and used for every greeting; the SSO bootstrap (`_bootstrap_owner`) fills the same field from the IdP's `name` claim, so both routes produce an equivalent account. Password policy adds `core.validators.EmailSimilarityValidator` (reworded similarity), `CharacterClassesPasswordValidator` (one lowercase + uppercase + number + symbol — this subsumes Django's `NumericPasswordValidator`, which is therefore not enabled), and `NoSequencesPasswordValidator` (no `aaa`/`abc` runs); the account page's live checklist (`password_checklist.js`) mirrors these. View tests that hit normal pages must mark onboarding complete (see `LoggedInTestCase`).
- **Password fields carry a reveal control**, added at runtime by `initPasswordReveals` (`app.js`) to **every** `input[type="password"]` on the page — login, account creation, the settings modal, password reset — rather than by each template, so a new password field can't ship without one. It also watches for **password-manager extensions** (1Password, LastPass, Bitwarden, Dashlane) claiming the right-hand end of the field and slides our button left via `.pw-reveal--shifted`. That detection is a **heuristic** — known injected-node markers plus a data-URI background-image check, re-run on a MutationObserver because extensions inject late — so an unrecognised one can still overlap; keep the offset in CSS, never as pinned pixels in JS. Note `.is-valid`/`.is-invalid` paint their own right-edge icon, so both the padding and `background-position` shift with it (same collision the 24h time inputs work around).
- **"Setup is finished" is not "the data exists"** (`core.onboarding.setup_finished` vs `is_setup_complete`). An import satisfies the data check the moment it lands — while the owner is still standing on Review — so keying the chrome or the funnel on `is_setup_complete()` handed them the running app before they pressed Finish (visibly: the nav pill appeared on `/help/` pages, which are exempt from the funnel). `setup_finished()` = session flag, else the data check **and** no surviving `OnboardingDraft`; the draft is the durable "still in the wizard" marker, deleted by `mark_complete` on Finish. Both `OnboardingRequiredMiddleware` and `core.context_processors.onboarding_status` use it, and the context processor also exports **`setup_in_progress`** so `base.html` keeps the wizard's minimal chrome on funnel-exempt pages. Note every path into the wizard must store a step (the Start step does) or the marker never appears — a test that POSTs straight to a later step will look finished when it isn't.
- **Help popup keeps you in the popup**: links inside an article body point at the full manual (a normal app page), so `help.js` intercepts any in-panel anchor matching `data-article-url`'s shape and calls `openArticle` instead — a quick look at a related article never navigates away, and mid-onboarding never escapes the wizard. The **Full manual** button is hidden while `onboarding or setup_in_progress`, for the same reason.
- **Onboarding wizard = six steps** (`core/onboarding.py` + the `Onboarding*View`s in `core/views.py`): **Account(1) → Start(2) → Tax(3) → Workplace(4) → Pay Terms(5) → Review(6)**. Step 2 (`OnboardingStartView`, `core/onboarding_start.html`) forks between **importing a BitGigs export** and **setting up from scratch**; the choice is stored in the draft under `start` but is **advisory only** — both routes stay reachable, and nothing reads it except the resume logic and Review's wording. Step 6 (`OnboardingReviewView`, `core/onboarding_review.html`) is **the single exit for both paths** — Pay Terms deliberately no longer finishes (its `goto in ("next","finish")` special case was removed so a crafted POST can't commit). All wizard logic lives in **`apps/core/onboarding.py`**, not `core/services.py` (that's the tax engine) — following the `dashboard_service.py` precedent; views stay thin. **"Next" skips a step the *database* already answers** (`_db_satisfied` in `resolve_goto`): after restoring a complete export, stopping on the Workplace step offered to create a *second* workplace beside the imported one. Only `in_db` counts — a draft the user typed is worth re-showing, since re-binding it shows their own input back — and a terms step whose rows are still the import's zero-pay stub is **not** skipped (that step is the only place to fix it). An explicit `onboarding_goto=<key>` jump is honoured as-is; only "next" skips. **`STEP_KEYS` is the single source of numbering** — `STEP_NUM`, `progress()` and `steps()` all derive from it, so a step can't be numbered inconsistently in two places. It is deliberately **three separate lists**: `STEP_KEYS` (display/order), `DRAFT_KEYS` (tax/workplace/terms — the only steps holding a draft payload) and `NAV_KEYS` (`onboarding_goto` targets). Collapsing them back into one is how this drifts.
- **Setup coverage + partial commit** (`core.onboarding.Coverage`/`Piece`/`coverage()`/`commit_setup()`): setup can be satisfied **either** by rows an import already wrote **or** by a valid draft Finish will write, so `commit_setup` writes **only what the database still lacks** — mixed mode (import supplies workplace+terms, user types tax by hand, or the reverse) works because the two gates are independent and absent draft keys are never touched. `can_finish` = `has_tax and has_terms`; **shifts never block** (they're informational on Review). Two traps encoded here: `workplace.in_db` filters `contracts__isnull=False` because an export may carry `"contracts": []`, creating a Workplace no term set can attach to; and `_terms_target_contract` attaches a terms draft to an imported contract **only when exactly one termless contract exists** — with several it refuses to guess rather than silently pinning pay terms to the wrong job. Third and subtlest: `perform_import` writes a **zero-pay placeholder term set** when a file's shifts name a workplace it never *defines* — a `Shift` is refused unless a contract is active on its date (`validate_shift_within_contract`), so without the stub those shifts are silently dropped. The stub is load-bearing, but it prices every one of those shifts at **0 kr** and satisfies the completion signal, so `Coverage.placeholders` (via `placeholder_termsets()` — any term set with neither an hourly rate nor a salary) **blocks `can_finish`**, and `OnboardingTermsView` **edits that row in place and saves immediately** rather than deferring to the draft (it already exists; adding a second term set would leave the stub covering the imported dates). One workplace per pass — Review routes to the next. The stub is an **implementation detail the UI never names**: the terms form is presented *blank* (binding it to the stub would prefill 0 kr and a year-2000 date) and the copy just says the workplace needs pay terms. Step 5 also renders **yellow, not green**, while one survives.
- **Review's other panels**: `Coverage.workplaces` lists every workplace with a ready/needs-terms flag; the **account card** reuses the settings modals verbatim via `core/_account_modals.html` (extracted from `settings.html` — both include it, so there is one copy of those forms). They post to `core:password-signin`, which now honours a same-origin **`next`** (`_signin_tab_url(request)`), or the wizard would bounce the owner to a settings page the onboarding funnel then redirects away from. **Start over** (`OnboardingResetView`, `/onboarding/start-over/`) discards the draft *and* the imported rows *and* the `EmailSettings` the hidden email step wrote (`reset_to_fresh()`) — those all write as they go, so clearing only the draft would leave behind exactly what the user asked to discard (the reported bug: email server config surviving a restart). It guards on **`session["onboarding_complete"]`, not `is_setup_complete()`**: a full import satisfies the database signal while the user is still legitimately on Review, and undoing an unwanted import is the whole point. `OnboardingReviewView.get` redirects finished users away, which is what keeps the reset form out of reach on a live install. The `transaction.atomic()` covers everything the *draft* contributes; rows an import wrote in an earlier request sit outside it and are never rolled back — the one place the wizard's "nothing is saved until Finish" rule legitimately doesn't hold. `mark_complete(request)` (shared with `OnboardingRequiredMiddleware`, which flips the same flag the moment the DB satisfies the signal — that can happen mid-wizard right after an import) sets the session flag **and** clears the draft. Tests: `apps/core/tests/test_onboarding_coverage.py`.
- **Onboarding import** (`OnboardingImportView`/`OnboardingImportConfirmView`, `/onboarding/import/…`): entered from Start, and again from Review to top up a partial file — so it is **repeatable**, and each run must see the workplaces the previous one created (`existing_workplaces` = the real queryset, **never `[]`**: with an empty list `detect_workplace_conflicts` stops flagging names and the `if name in conflicts` overlap filter silently disables overlap protection). Thin wrappers over `data_io.services` — the same code path Settings → Import uses, only the entry/exit URLs differ — living under `/onboarding/` so the middleware exemption covers them. It **writes immediately** and always exits to Review; it never decides completion itself. The shared review template `data_io/import_confirm.html` takes its endpoints from **`confirm_url`/`cancel_url` context vars** (don't reintroduce hardcoded `{% url 'data_io:…' %}`) and renders the step indicator when `onboarding` is set. Helpers in `data_io/services.py` keep the two flows in step: `import_summary`, `build_workplace_mapping` (anything unrecognised → `skip`, so a tampered form can only import *less*), `describe_import`, the `workplaces_created`/`termsets_created` counts (`_create_workplace_from_dict` returns `(wp, n_termsets)`) — without those a workplaces-only file reported "nothing to import" while visibly creating one — and **`describe_conflicts`**, which annotates each unmatched name with `defined`: whether the file actually *describes* that workplace or merely *names it on a shift*. Those produce very different workplaces, so the review page offers **three creation choices**, not one: `create` (restore the file's settings/contracts/terms — only offered when `defined`), **`create_blank`** (`_create_blank_workplace`: name + stub contract only, deliberately ignoring what the file says) and `skip`. Both blank paths go through the same helper, so "blank workplace" means exactly one thing. Tests: `apps/core/tests/test_onboarding_import.py`.
- **Orphaned workplace-icon cleanup** (`workplaces.services.prune_orphan_icons` / `maybe_prune_orphan_icons`): deleting a `Workplace` leaves its uploaded `custom_icon` on disk (Django's `FileField` never removes files), so `media/workplace_icons/` accumulates orphans. `prune_orphan_icons()` deletes every file there that no `Workplace.custom_icon` references (compared by basename). There is **no cron** in this app, so it runs **opportunistically**: `DashboardView.get` calls `maybe_prune_orphan_icons()`, which runs the prune **at most once per `ICON_PRUNE_INTERVAL` (24 h)** — gated by the mtime of `settings.ICON_PRUNE_MARKER_PATH` (`instance/last_icon_prune`), stamped *before* the prune so a failure can't make every request retry, and it **swallows all exceptions** so housekeeping never breaks the page. The automatic sweep is gated on **`settings.ICON_PRUNE_AUTO`** — **on in `base.py`, off in `local.py`**: the prune treats the active DB as the sole authority on which icons are used, which is only true in production; a dev checkout often keeps a `db.sqlite3.bak` pointed at the same `media/`, whose icons would look orphaned to the live DB. Manual/scheduled entry point (ignores the flag — running it is deliberate): `manage.py prune_workplace_icons [--dry-run]`. Tests point `MEDIA_ROOT` + `ICON_PRUNE_MARKER_PATH` at a temp dir (`apps/workplaces/tests/test_icon_prune.py`).
- **Optional SSO (any OIDC provider)**: `django-allauth` is **always installed** (one migration state for every deploy), but the OIDC provider is only registered when `OIDC_SERVER_URL`/`OIDC_CLIENT_ID`/`OIDC_CLIENT_SECRET` are all set — `settings.SSO_ENABLED`. `SSO_PROVIDER_ID` is `"sso"` and lands in the callback URI the IdP must have registered (`/accounts/oidc/sso/login/callback/`), so renaming it forces every operator to re-register that URI. **BitGigs must stay feature-complete standalone**: with those unset it is exactly as before (native password login, no SSO button, no IdP required). Django's auth URLs are included **before** `allauth.urls` in `bitgigs/urls.py` so the native `/accounts/login/` and `/accounts/logout/` keep winning; allauth only supplies `/accounts/oidc/…`. Because the app is **single-tenant** (`Workplace`/`TaxProfile`/`UserSettings` have no user FK, so every `User` sees the same data), SSO **must never create a User** — `core.adapters.OwnerOnlySocialAccountAdapter` links an incoming identity to the single existing owner only when the email matches, and refuses everything else; `NoSignupAccountAdapter` closes allauth's own signup route. The one exception is the **fresh-install bootstrap**: with no owner yet, an identity coming through the account step's SSO button becomes the owner (no password set) — but only behind the setup-key session flag. Two auth backends are now configured, so any manual `auth.login()` call **must name its backend** (see `OnboardingAccountEmailView`).
- **SSO flows**: an identity from the IdP never lands silently — it is parked in the session and shown on a **confirm page** (name / email / uid, read via `core.adapters.claim` from the raw claims, *not* `sociallogin.user`: allauth drops an invalid email and splits `name` on a space, which doubles authentik's surname). That applies to the fresh-install bootstrap (`OnboardingAccountConfirmView`) **and** to linking from the settings page (`SSOLinkConfirmView`, `process=connect`) — with a live IdP session the round-trip is instant, so you would otherwise bind whichever account it happened to hold. A plain login is deliberately *not* interrupted. `/sso/launch/` is meant to be the **Launch URL of the IdP's application**: opening BitGigs from the IdP dashboard signs you in, or offers to link when you're signed in locally but unlinked. "Not you?" (`/sso/idp-logout/`) is RP-initiated logout to the IdP's `end_session_endpoint` — no `post_logout_redirect_uri`, so nothing needs registering; authentik's own signed-out page takes it from there. (`prompt=login` would be tidier but authentik ignores it on repeat attempts.) The hand-off pages render with `minimal_chrome` (see `base.html`): centred logo, nothing clickable, so a stray nav click can't strand the round-trip.
- **Sign-in management** (settings page's **Sign-in** tab, `PasswordSignInView`): edit the account's display name + email (`AccountDetailsForm`, `action=account_details` — since the username **is** the email it rewrites `username` and `email` together, and caps the email at `User.username`'s 150 chars, not `User.email`'s 254), set/change the password (a modal reusing the account step's `password-box` + live checklist — `password_checklist.js` drives any form with `data-pw1-id`), turn password sign-in off (`set_unusable_password`), or unlink the IdP. Changing the email does **not** break an existing IdP link (`pre_social_login` returns early on `sociallogin.is_existing`, matching by uid) — but a *re-*link would then need the new address to match. One invariant runs through all of it — **at least one way in must survive**: the password can only be turned off while an identity is linked, and the identity can only be unlinked while a usable password exists. Always `update_session_auth_hash` after any password change, or it logs the owner out of their own session. `BitGigsLoginView` hides the password box entirely when password sign-in is off (a form that cannot succeed is a trap) — but never when `SSO_ENABLED` is false, which would lock a standalone owner out. There is no email backend, so account recovery is `manage.py changepassword`; the login page's "Forgot your password?" / "Can't access <provider>?" modal says so. The tab renders **with `SSO_ENABLED` false too** — password management must not be gated behind an IdP, or a standalone owner has no in-app way to change their password — and in that state it shows a tinted "not configured" panel naming the three `OIDC_*` env vars plus the `OIDC_PROVIDER_*` branding ones. Only the IdP link/unlink and "turn password sign-in off" controls are SSO-gated.
- **SSO button branding** (`core/sso.py`): BitGigs works with **any** OIDC provider, so **no template, view or message may name one** — they all print `{{ sso_brand.name }}` (or `get_brand().name` server-side), supplied to every template by the `sso_status` context processor. `get_brand()` resolves four optional env vars per field, each falling back to the next: explicit `OIDC_PROVIDER_NAME`/`_COLOR`/`_ICON` → the `OIDC_PROVIDER_BRAND` preset → BitGigs' neutral default (`"SSO"`, `--primary`, a `bi-shield-lock` glyph). `PRESETS` holds **only `authentik`** — a preset means vendoring another company's trademark, so the bar is high; everyone else points `OIDC_PROVIDER_ICON` at their own file in `assets/static/graphics/`. Three rules the code enforces and tests pin: `text_color` is **derived** from the colour's WCAG luminance (a pale brand colour must not render white-on-white) — *except* when a preset states its vendor's own `text` and the operator hasn't overridden the colour, because a preset exists to reproduce branding, not to second-guess it (on authentik's `#fd4b2d` dark text scores better, but they brand with white); `tint_icon` is true **only for a bundled preset icon** — an operator's own logo is never recoloured; and `tint_invert` makes that tint follow `text_color`, or a dark-text button gets a white mark floating on it. A malformed `OIDC_PROVIDER_COLOR` falls back to the default instead of emitting broken CSS. The button itself is one partial, `core/_sso_button.html` (`sso_label`/`sso_process`/`sso_next`/`sso_btn_class`), used by the login page, the onboarding method step and the settings page's Link control; it sets `--sso-bg`/`--sso-fg`/`--sso-ring` inline for `.btn-sso`, which is why that CSS names no colours. `core/_sso_brand_icon.html` is the card-header variant (untinted, since the header is a light surface).
- **Outgoing mail** (`core/mail.py`, `core/mail_backend.py`, `core/crypto.py`): the SMTP config lives in **`MailConnection` rows** (one per setup — held in the DB, not env vars, because the whole point is configuring *and testing* it from Settings → Email without a redeploy), and **`EmailSettings` is now a slim singleton** holding only the *global* concerns: the master `enabled` switch, `allow_password_reset`, and a **role→connection map** (`system_connection` / `calendar_connection` FKs). A **role** picks which connection sends which kind of mail: `EmailSettings.ROLE_SYSTEM` (password reset + anything transactional) and `ROLE_CALENDAR` (calendar invites). `connection_for(role)` returns the assigned FK **or the default connection** (`MailConnection.default()` = the `is_default` row, else the first) — so the common "one server, both roles" case is a single connection with the FKs left null. `MailConnection.save()` enforces **at most one `is_default`**. `EMAIL_BACKEND` is `core.mail_backend.DbConfiguredEmailBackend` — a stock SMTP backend that resolves its connection from a **`role` kwarg** (default = system) at connect time; that's what lets code that knows nothing about BitGigs (Django's own password-reset views, which hit the *default* connection) send from the system mailbox, while calendar invites do `get_connection(role="calendar")` (see `calendar_sync.invites._send_mail`) to send from the calendar mailbox. `mail.send_mail()`/`build_connection()`/`from_address()`/`diagnose()` all take a **`MailConnection`** as their `config` (default = the system role's). The **password is encrypted at rest** (`core.crypto`, Fernet keyed off `SECRET_KEY`) on the *connection*; read it only via the `password` property, which also applies the `EMAIL_HOST_PASSWORD` env override. `decrypt_secret` returns **`None`** (not `""`) when `SECRET_KEY` has rotated — "unreadable", distinct from "unset" — and `password_unreadable` surfaces it as a "re-enter the password" prompt. `MailConnectionForm`'s password field is **write-only**: blank means "keep the stored one". Two forms, two POST endpoints: `EmailSettingsForm` → `core:email-settings` saves the master switch + role map (and refuses to enable mail until the system role resolves to a configured connection); `MailConnectionForm` → `core:mail-connection-save`/`-delete`/`-default` manages the connections (a blank `pk` creates; the first connection auto-becomes default; delete promotes a new default). **`mail.diagnose()`** is the feature's reason to exist: it walks config → DNS → TCP → TLS → AUTH → optional real send as *separate reported stages*, so the first ✗ names the wrong setting; it does a bare `socket` connect before `smtplib` so a closed port reads as a closed port. The optional send stage is the only one that catches a refused from-address. **The Email tab lists each connection read-only** (name / server / from / last-test badge / default star), with the edit form behind an **Edit** button in **one shared modal** (`core/_email_settings_modal.html` + `core/_email_form_body.html`, grouped Name/Server/Sign-in/Sender/Options): "Add connection" opens it blank, a card's Edit fills it from the card's `data-*` via `email_settings.js` (only **one** form exists, so crispy IDs stay unique). Per-card **Test** checks that saved connection (posts `connection=<pk>` to `core:email-test`); a separate **Send a test message** panel sends a real message through a chosen connection. Validation errors re-render with `email_modal_open` (server-rendered bound form). A **Clear all** button (`core:email-clear`, `reset_to_fresh()`) drops every connection and disables mail. `email_settings.js` rewrites each connection's **live "Last test" badge** (`#emailLastTestBadge-<pk>`) from the test JSON (`run_and_record` still persists it).
- **Email activity log** (`EmailLog` model, `core:email-log`/`email-log-ack`): every send attempt is recorded — recipient, subject, ok/fail, the **`connection_name`** that sent it (denormalised, since connections come and go), and the failure reason (never the body). Two choke points cover *all* mail: `DbConfiguredEmailBackend.send_messages` logs real app mail (`kind="sent"`; this is the only point that catches Django's password-reset mail, which never touches `mail.send_mail`), and `mail.run_and_record` logs the diagnostic **test send** (`kind="test"`, only when `send_to` was given — a connection-only test writes no row, it's already in `last_test_ok`). `EmailLog.record` **prunes to `PRUNE_KEEP=200`** (mirrors `HelpArticleRevision`). Successes are stamped `acknowledged_at` immediately; only **failures** are ever unacknowledged. `EmailLog.objects.failures_unseen()` (`ok=False, acknowledged_at__isnull=True`) drives a **red dashboard banner** (`DashboardView` context `email_failures_unseen`, dashboard-only, no context processor) that clears **only on explicit Dismiss** — a POST to `EmailLogAckView`, reachable from both the banner and the log page (honours a same-origin `next`); *viewing* the log does not clear it. The log's success pill reads **"Accepted"**, not "Sent", and both the page and the help article spell out that SMTP acceptance is *not* proof of delivery (a bad address bounces back asynchronously minutes later — deliberately **not** chased with an IMAP bounce-poll, which would be a third integration). Two smaller Email-tab touches: `email_settings.js` **auto-fills the From address from the username while From is still blank** (backs off once it's edited, mirroring the help-slug rule), and password-reset state is **editable from the Sign-in tab too** (`sign_in_context` exposes `password_reset_allowed`/`email_configured`; the switch posts `action=password_reset` to `core:password-signin`, which writes the same `EmailSettings.allow_password_reset` the Email tab owns — it needs a mail server to work but is a sign-in feature to use, and being sent to another tab to flip one switch is what makes a setting hard to find. It **auto-submits** via `data-autosubmit` (settings.js), and warns in place when it's on with no working mail server) as well as shown as a row on the Email overview summary.
- **Password reset** (`BitGigsPasswordReset*View`, templates in `assets/templates/registration/`): `django.contrib.auth.urls` already routed these, so the subclasses exist for three reasons only — the flow **redirects to login unless `password_reset_available()`** (mail configured *and* `allow_password_reset`), the public request form is **rate-limited per IP** (5/hour, cache-backed; the client IP comes from `X-Forwarded-For` only when `DJANGO_TRUST_PROXY_IP` is set — the header is spoofable without a proxy), and the From header comes from `EmailSettings` rather than `DEFAULT_FROM_EMAIL` (which BitGigs never sets). The **confirm** view is deliberately *not* gated — a link already in an inbox must keep working if mail is later turned off. `extra_email_context` overrides `domain`/`protocol` with `request.get_host()`: `django.contrib.sites` is installed (allauth needs it) and would otherwise build every link from the unedited Site row, i.e. `example.com`. The HTML email is the **one place literal colour hexes are allowed** — mail clients don't support CSS custom properties — and even there the accent is passed in from `UserSettings`, not hardcoded. Console recovery (`manage.py changepassword`) stays documented everywhere as the fallback for when mail itself is what broke. The login page's **recovery modal + "Forgot your password?" link are always rendered** — `changepassword` works with no mail server and no IdP, so hiding recovery would strand a standalone owner; only the *emailed*-link button inside it is gated on `password_reset_enabled`, and the console hint prints a **placeholder** address (`your@email.address`), never the owner's real username — the login page is public, so leaking it there is a user-enumeration gift.
- **HTTP API** (`apps/api/`): read-only JSON endpoints under `/api/v1/`, authenticated **only** by `Authorization: Bearer bg_…` API keys (a logged-in session deliberately does not count). `ApiKey` stores a **SHA-256 hash**, never the key — unlike the SMTP password there is nothing to replay, so "view once" is the point: `ApiKey.issue()` returns the raw key exactly once, the create view parks it in the session (`SESSION_NEW_KEY`), and the Settings → API tab pops + reveals it on the next render only. The stored `prefix` is **admin-only** — by the owner's explicit choice the tab never shows any part of a key after creation (the list shows Created instead), so don't reintroduce a prefix column. Keys have a nickname, optional `expires_at`, revocation (`revoked_at`; delete is refused while a key is still active), `last_used_at` stamping, and **granular scopes** (`scopes` JSON list of endpoint ids, or `["*"]`). `api/registry.py` is the single source of truth for endpoints — it drives the scope checkboxes, the docs accordion with generated **sample Python requests**, and the scope check; adding an endpoint = add the view (subclass `ApiEndpointView`, set `endpoint_id`; **only the base class may define `dispatch()`** — same `login_not_required`-on-dispatch caveat as `_AccountStepView`) + one registry entry. Auth failures name themselves (`missing_key`/`invalid_key`/`revoked_key`/`expired_key` 401, `insufficient_scope` 403). `/api/` is exempt from `OnboardingRequiredMiddleware` (JSON must never answer with a wizard redirect); the key-management POSTs (`api:key-create`/`key-revoke`/`key-delete`) are normal session-gated views. The income endpoint computes nothing itself — `api/services.py` calls `AnalyticsService.project_period` with the stored `UserSettings`, so API and Analytics page can't disagree; Decimals go out as strings (`"12345.67"`). Stdlib-only CLI client: `scripts/api_client.py` (`ping` / `income`, `--json` for raw output).
- **Task scheduler** (`apps/scheduler/`): for jobs that must **fire with no user present** (night-before invite send, daily digest…). The chosen shape is **Shape A** — a **standalone `manage.py run_scheduler` process** (one code path in dev/bare-prod/Docker), **never an in-process thread** (gunicorn's several workers would each fire it). Opportunistic request-triggered housekeeping (`maybe_prune_orphan_icons`) stays the fallback for maintenance jobs that *don't* need to fire unattended — the scheduler is **optional**, nothing forces it on. **`registry.py`** is the single source of truth for jobs (mirrors `api/registry.py`): each `Job` = id/title/description + a zero-arg callable + exactly one cadence (`every=timedelta` **or** `daily_at=time` local). **`ScheduledJob`** is the DB-backed *schedule table* — one row per job, seeded from the registry default by a `post_migrate` hook (`signals.seed_scheduled_jobs`: creates missing rows, deletes rows for jobs no longer registered, **never** overwrites an existing row's operator-tuned cadence/enabled). The row holds the live cadence + `enabled` + runtime state (`next_run_at` decides due-ness; `last_run_at`/`last_status`/`last_error`/`last_duration_ms`). Editable in the **Django admin** (no settings-page tab yet). Engine in **`services.py`**: `compute_next_run` schedules a **single future slot**, so an overdue daily job fires **once**, not once per missed day; `claim()` advances `next_run_at` via an **optimistic compare-and-set** (`filter(pk, next_run_at=old).update(...)`, works on SQLite + Postgres, no row locks) *before* running, so a stray second loop can't double-fire; `run_job` **never raises** (a failing job is caught, logged, stamped on the row). The `prune_workplace_icons` job **honours `ICON_PRUNE_AUTO`** exactly like the opportunistic path (no-ops in dev where a `db.sqlite3.bak` shares `media/`). **Settings → Jobs tab** (`scheduler/_settings_tab.html` + `scheduler.views.jobs_settings_context` / `ScheduledJobToggleView`, POST to `scheduler:job-toggle`, redirects back to `?tab=jobs` — same shape as the API tab): **three panes** — *Scheduler process* (the liveness banner), *Scheduled jobs* (a read-mostly table: Job / cadence / next run / last run + OK/Failed badge / on-off switch that **auto-submits** on change, each row expandable for description, identifier, duration and last error) and *Task queue*. It's the friendlier surface over the Django admin (which is also registered). The tab is **live**: `js/jobs_settings.js` polls **`scheduler:status`** (`SchedulerStatusView`, JSON) every 5s — pausing while the browser tab is hidden and giving up after 5 consecutive failures — and updates the heartbeat banner, each job row's next/last run + badge + open detail panel, and the whole queue table in place. Server-rendered first paint and the JSON come from the **same serializers** (`_task_payload`/`_job_payload`/`scheduler_status()` in `views.py`) and the JS row builder **mirrors the template's queue markup**, so keep the two in step. The queue table shows every pending/running row plus the newest **`RECENT_TASK_LIMIT`** finished ones (**60**, with the overflow counted in a footer note — at 10 a 31-shift invite batch visibly ate its own history as it drained, which reads as rows vanishing rather than as a display cap); `.queue-table` is `table-layout: fixed` so a long SMTP error **wraps** instead of squeezing the other columns flat. Queue rows are cleared by **`scheduler:tasks-clear`** (`TaskQueueClearView`, POST `scope=done|failed|all`); *done* and *failed* are **separate buttons on purpose** — a failed row is the only visible trace of an invite that silently never sent, so binning those is a deliberate press behind a confirm. Pending/running rows are never *deletable* from the UI (the scheduler owns them) — but they are **cancellable**, see the watchdog below. A failed row also carries a **Retry** button (**`scheduler:task-retry`** / `TaskRetryView`, POST `id=`, offered only while a handler for that task id is still registered — `_task_payload`'s `can_retry`): nothing auto-retries (a re-sent invite duplicates in the inbox), so this is the manual second attempt, and it is the **only** route for work whose origin is gone — a calendar **CANCEL** whose shift was deleted has no chip, no modal and no sweep left to press. It enqueues a *fresh* row (`label_note="retry"`, history of both attempts kept) with **`queued_at` re-stamped to now**, which is what makes it a deliberate probe past the mail circuit breaker, and deletes the failed row **without** firing `on_clear` — retrying is the opposite of dismissing. Clearing a **failed** row fires that task's **`on_clear(payload)`** hook (declared on `@register`, dispatched by `tasks.run_clear_hooks`, never raises): binning the record of a failure is how the owner acknowledges it, and the owning app decides what that means — the scheduler core still imports no feature app. A payload may also set **`label_note`**, which `ScheduledTask.label` appends in brackets, so a retry reads "Send calendar invite (retry)" next to the attempt it follows. **Stuck-task watchdog** (`services.stuck_tasks`/`reap_stuck_tasks`, `SCHEDULER_TASK_TIMEOUT_SECONDS` = **600**): a task is flipped PENDING → RUNNING *before* it runs, so a process that dies mid-task leaves a row **nothing can reach** — `claim_task` only takes PENDING, Clear only takes finished rows, Retry only offers itself on FAILED. The loop therefore reaps RUNNING rows older than the timeout into FAILED **first thing each tick**, before `run_due`/`run_pending_tasks`. It can't *stop* a run genuinely still going; if that process later finishes it overwrites the row with its real outcome, which is honest either way. The timeout is generous **on purpose** — it exists to catch a dead process, not to time out slow SMTP. Reaping (and the manual cancel) fires the row's **`on_abandon(payload, reason)`** hook — the sibling of `on_clear`, and the reason it's needed: the handler records its own outcome (`calendar_sync.tasks.run_send_invite_mail` → `mark_send_ok`/`mark_send_failed`), so a row that never *reached* its handler's failure path is precisely the case nothing recorded, and without the hook the shift keeps an "invite sent" marker for a message nobody received (`calendar_sync.tasks.abandon_invite_mail` → `invites.mark_send_failed`). **`TaskCancelView`** (`scheduler:task-cancel`, POST `id=`) is the manual counterpart, offered on **every** pending/running row: the reap needs a live scheduler to do it, and "no scheduler" is exactly what strands a row. It marks the row **failed, never deletes it** (same reasoning as a rejected send — it's the visible record, retryable, and clearing it later is the ordinary acknowledgement) and fires `on_abandon` too. `_task_payload` carries **`stalled`** (running past the timeout) and **`can_cancel`**; the Jobs tab **reports** stalled rows but **never reaps** — a page load must not fire `on_abandon` hooks, so `scheduler_status()` only reads `stuck_tasks()` ids. **One-off task queue** (`ScheduledTask` + `scheduler/tasks.py`): the async hand-off for slow request-triggered work (sending a calendar invite over SMTP without blocking the page). An app registers a handler with `@scheduler.tasks.register("id", title="Human label")` (imported from its `AppConfig.ready()`, so the scheduler core imports no feature app; the optional `title` is what the queue table shows instead of the bare id — `tasks.title_for` / `ScheduledTask.label`, which falls back to the id) and calls `enqueue("id", payload)`; the loop drains due tasks each tick via `services.run_pending_tasks` (claim via the same compare-and-set, `process_task` never raises, retries with backoff while `attempts < max_attempts` — **default `max_attempts=1` so a test invite never double-sends**, finished rows pruned to `PRUNE_KEEP=200`). **`SchedulerHeartbeat`** is a one-row table the loop stamps every tick; `is_alive()` (beat within `max(90, 3×tick)`) lets a view warn that a queued task won't send because no scheduler is running — surfaced as a **liveness banner + live queue table on the Jobs tab**, and as a warning on the calendar invite send/test paths. **`SCHEDULER_TASK_EAGER`** (default off; a test flips it on with `@override_settings`) makes `enqueue` run the handler **inline** instead of queuing — the "always eager" switch so tests can assert a queued send's effect without spinning the loop. `SCHEDULER_TICK_SECONDS` is **10** (lowered from 30 so queued tasks send promptly). Run model: dev = `python scripts/dev.py` (stdlib launcher: runserver + run_scheduler in one console, forces `--settings=bitgigs.settings.local`, Ctrl+C stops both). Two dev-loop details, both learned the hard way: **`run_scheduler` runs under Django's autoreloader when `DEBUG`** (`--no-reload` opts out, `--once` never reloads) — without it the loop keeps executing the code it started with while runserver quietly reloads, so an edited task handler silently doesn't take effect and reads as "the feature is broken"; and **`dev.py` takes a single-instance lock** (`instance/dev.lock`, an OS byte-range lock so nothing goes stale after a crash; `--allow-multiple` overrides), because a second stack means a second scheduler draining the same queue, which doubles the rate mail leaves the server and trips a provider's sending limit on its own. Both children now run their work in a grandchild (the reloader's), so `dev.py` stops them with `taskkill /T` on Windows rather than orphaning it. **Ctrl+C is a supported stop, not a crash**: `dev.py` installs its own SIGINT/SIGBREAK/SIGTERM handler that sets a flag the poll loop watches (so shutdown happens at a known point), treats a child exiting with `STATUS_CONTROL_C_EXIT` (`-1073741510`) as *that stop* rather than a failure — the console Ctrl+C reaches the children first, and it used to be reported as `[dev] runserver exited (…)` with a non-zero exit code — and swallows further presses during the shutdown wait (`_wait`), where a second Ctrl+C used to escape the `finally` as a traceback. `run_scheduler.handle()` catches `KeyboardInterrupt` for the same reason: `services.run_due`/`run_pending_tasks` guard on `Exception`, which a `BaseException` walks straight past, and `manage.py` would print the traceback over the shutdown. bare prod = two systemd units (`deploy/systemd/`); Docker = a `scheduler` compose sidecar reusing the image with `command: python manage.py run_scheduler`. Loop cadence = `SCHEDULER_TICK_SECONDS` (10). Tests: `apps/scheduler/tests/test_scheduler.py`.
- **Theming — one colour source of truth**: the `:root` token block in `assets/static/css/style.css` (light) + its `[data-bs-theme="dark"]` override (only base tokens flip; every tint is `color-mix()`-derived so it re-resolves per theme/accent) + a `--bs-*` bridge that makes stock Bootstrap follow. **Never hardcode a colour hex** in CSS/templates/JS — use a token (`var(--surface)`, status families `--success/--info/--warning/--danger` each with `-tint`/`-strong`, `--cal-*`, `--chart-*`, `--shadow-rgb`…). In JS, assign `'var(--token)'` strings to `el.style.*` (they resolve live); only canvas consumers need real values via `window.themeToken(name)` (app.js) / `window.chartPalette()` (`chart_theme.js`, loaded by the two analytics templates and setting `Chart.defaults` chrome). Per-workplace colours (`wp.color`, `--wp-accent`, avatar backgrounds) are **DB data, not theme** — they stay inline; only their `#6366f1` *fallback* is `var(--primary)`. **A workplace's own pages wear that workplace's accent via `.wp-accent-scope`** — a wrapper that *re-points the theme tokens themselves* (`--primary`/`--primary-rgb`/`--secondary`, the derived `--primary-tint`/`-border`/`-strong`, the `--bs-*` primary+link bridge, `--cal-today`/`--cal-week`) at the inline `--wp-accent`, so every rule that already follows the app accent follows the workplace with no per-rule work: gradient buttons, links, breadcrumbs, switches, focus rings, `.bg-primary` badges, stat-card hover, the calendar washes. The `--bs-*` and derived tokens **must** be re-declared — they are declared at `:root`, so `var(--primary)` resolves *there* and inherits down as a fixed value; redefining `--primary` deeper never reaches them. Two hard rules, both enforced by the `{% wp_accent_scope wp "extra classes" %}` simple_tag (`workplaces/templatetags/wp_accent.py`, which emits the whole `class=` attribute — don't write a second one beside it): the class and **both** `--wp-accent`/`--wp-accent-rgb` are emitted together (`--primary-rgb` can't be derived from a hex, and without it `.bg-primary` and the focus ring resolve to nothing), and **nothing is emitted at all without an accent colour** — a `--wp-accent: var(--primary)` fallback is a custom-property *cycle*, which invalidates both tokens and drains the colour out of everything inside the scope. `Workplace.accent_rgb` supplies the triplet (empty, i.e. no scope, when unset or unparseable). Applied to: workplace detail (whole content block, so the customize/crop/SVG modals inherit it), workplace form, contract form, termset form, both delete-confirm pages, `approve_shifts.html` and the payslip editor (`payroll/period_detail.html`). **Not** the navbar or the help FAB. `.accent-btn-group` (the pay-terms segmented pickers) and `.supersede-prompt` are keyed on `--primary`, not `--wp-accent`, so they follow the app accent outside a scope (onboarding) and the workplace inside one; the segmented group's selected half uses the same travelling gradient as `.btn-primary`/`.choice-group`. The old `.accent-form` class is gone. `.workplace-accent-banner` takes its colour from the scope (`var(--wp-accent)`) and carries its own glow — don't re-add an inline `background`. Tests: `apps/workplaces/tests/test_accent_scope.py`. Cards keyed to a workplace (dashboard, `/workplaces/`, planning's `.wp-card`) carry a **gradient wash of that workplace's accent** that must resolve to plain `var(--surface)` before it reaches any text — the wash sits behind the avatar only, never under a label. - **Analytics income projection** (`AnalyticsService.project_period`) buckets by **payroll period, not calendar month** — `_period_bounds` delegates to `PayrollPeriodService.resolve_period_bounds`, so a 20th→19th job's shifts worked 20–31 July land in the **August** row (the month they're paid in).   - **A row is a mix of certainty bands, not one label.** `MonthRow` holds three `PayPart`s (`actual`/`planned`/`projected`, each hours+gross+net) and derives `hours`/`gross`/`net`/`is_planned`/`is_projected`/`state`/`is_mixed` from them. `state` names the row's **least certain** band (`actual` / `actual-planned` / `planned` / `projected` / `inactive`) — a total is only as certain as its weakest ingredient. `PayPart.active` exists because a band can be **in play while amounting to nothing**: a future period with no history projects *zero* hours, and without the flag `any` would be False and the row would read as a worked zero. Known pre-existing bug *not* fixed here: `_combine_estimates` sums `monthly_deduction`, so a **mid-period raise** (two term sets in one period) double-counts it — on the dashboard, workplace page and payslip editor too.
  - **Hourly hours are grouped by the term set active on each shift's own date** (`_hours_by_termset`), so a raise mid-period prices the days before it at the old rate. Planned shifts count only from **today onwards** — one rule covering all three cases (a future period is entirely on/after today, a closed one entirely before it, the current one splits at today); an earlier planned shift should have been approved by now and counting it would double up with the approved hours that replaced it. Gated by `UserSettings.use_planned_shifts` (default on).
  - **The projection fills only a period holding nothing real** (`projected_basis` = not past, zero actual, zero planned). A closed period is whatever was worked, **including zero** — a fact, not a gap to guess at — and a period that already has hours must not have an average added on top, since those hours are part of what the average predicts. Projected hours are **day-prorated** by the days the contract actually covers (`active_day_split_range`), so a job ending on the 15th isn't credited a whole period.
  - **Every period projects from its own trailing window** — `project_period` keeps a rolling `window` list (seeded by `_seed_window` with the periods *before* the visible range, so January still has history) and pushes each period's resolved `row.hours` as it goes, aggregating the last `trailing_months` entries with `_aggregate`. One average computed at `today` and reused gave every future month the identical figure. **The window must be fed resolved hours, not approved ones**: approved-only empties it as it advances into the future and decays every projection toward zero, so it carries approved → still-planned → (past the last real data) what the previous period itself projected. Two exclusions, both via `_hourly_period_hours` returning `None` — which the window *skips* rather than counting as zero: a period with no contract (pre-hire zeros would sink a new job's average) and a period the workplace was **salaried** (those logged hours were never paid hourly, so pricing them at an hourly rate invents income). The window averages **hours**, priced at each period's own rate — averaging past *income* instead would project pre-raise earnings forward and swallow a raise.
  - `trailing_average_hours` is now only the workplace card's **headline** figure (anchored at `today`, approved hours over **closed** periods via `_trailing_periods`, which tests `period_end < ref` so a finished offset period isn't skipped). It is deliberately *not* the forecast, so it can legitimately differ from what the projected periods show.

That tab shows a **read-only** per-contract overview table linking to the contract page. Recipients are a **single** per-contract address, not the old multi-line list. All `.form-check-input` switches/checkboxes follow `--primary` (accent), not Bootstrap blue. **All invite mail is sent off-request via the scheduler queue**, at the single **`invites._send_mail`** choke point: it no longer sends inline — it `enqueue`s a `calendar.send_invite_mail` task (ics base64 in the payload, **`max_attempts=1` — no auto-retry**, because a retry re-sends the email: the calendar client dedupes the event by UID+SEQUENCE but the inbox shows a duplicate, so a failed send fails *visibly* on the Jobs queue instead), and the handler (`calendar_sync/tasks.py`) calls the real synchronous sender **`_send_mail_now`**. So every path — bulk "Send invites" (`SendInvitesView`), per-shift, `reconcile.sync_all`, and the **`post_delete` CANCEL signal** — returns instantly and shows in the Jobs queue; the `ShiftInvite` bookkeeping (uid/sequence/`last_recipients`) stays **synchronous** so counts stay accurate. **`invites.month_sweep(year, month)` is the single answer to "what would Send invites do?"** — a list of `SweepGroup`s (workplace, `new`, `updates`, `recipients`), and the **one** place that scope is derived. Three callers used to work it out separately, which is how the button came to offer sends the server then skipped: `SendInvitesView.post` performs it, `SendInvitesView.get` **previews** it as JSON for the confirm modal, and the planning view's `invite_pending_count` is just `sum(g.total …)`. It is **scoped by payroll period, not the visible grid**: for each workplace active that month, only PLANNED shifts within `PayrollPeriodService.resolve_period_bounds(wp, year, month)` — so an offset job's next-period shifts (e.g. a 20th→19th period's days after the 20th, shown greyed as `.shift-chip--prior-period`) aren't swept in; they're offered when you view that month. The grid is padded to whole weeks *and* to the union of every workplace's period, which is why counting *it* left the button offering a send that was already complete. Two membership rules: the idempotency skip (`shift.invite_uid in active_uids`) means a per-shift manual send isn't re-sent, but such a shift lands in `updates` when `needs_send` (edited since, or its send was rejected); and a shift with **no resolvable recipient is omitted** — `activate` refuses it, so counting it would promise a send that never happens. **Pressing the button opens `#sendInvitesModal`** (markup in `planning.html`, driven at the end of `planning.js`) rather than a `window.confirm`: it fills from the GET preview — every workplace, the new-vs-update split, the exact addresses, and a warning when `SchedulerHeartbeat` is down — because the press mails real people, and "N invites to these addresses" is the only form of that question worth asking. Nothing is sent until the modal's own confirm POSTs. That count is fixed at **render** time, so `planning.js`'s **`noteInvitePending(shift)`** flips the disabled "All invites sent" button back to "Send invites" when a newly planned shift needs one — called from all three chip-insert paths (copy-paste, fast create, modal create), since chips are inserted without a reload. It re-checks the *same* three conditions server-side (`invite_eligible`, no active invite, `isInPeriod`), so the client can't offer a send the server would skip.
- **Stale invites** (`ShiftInvite.content_key` + `invites.event_fingerprint`/`is_stale`): invites are still never re-sent silently, but an edit no longer leaves the recipient holding wrong details unnoticed. `event_fingerprint(shift)` hashes exactly what reaches the invitee — date, times, break, type, and the **resolved title + location** — so a `notes` edit is not a change but a contract's title override is. `_dispatch` stamps it on every **REQUEST** (never a CANCEL, which ends the series); `is_stale` compares it and is False for past shifts, for **approved** ones (`_is_approved` — approval carries `invite_uid` onto the `Shift` so the invite stays live and deletable, but the row now records *hours worked*: correcting a start time because you arrived early is bookkeeping, not a change of plan to mail about, and without this the approve flows' own edit popped the re-send prompt) *and* for a blank `content_key` ("unknown", not "changed"). That blank-is-safe rule needs its counterpart or the feature is **inert on every existing install**: migration `0004` runs **`invites.backfill_content_keys()`**, stamping each live invite with its shift's *current* fingerprint ("the invite matches this") so edits start prompting immediately. That migration deliberately imports the real `calendar_sync.invites` rather than using `apps.get_model` — the fingerprint needs `ContractCalendarConfig.title_for`/`location_for`, which historical models don't carry — and swallows failures, since a backfill must never block a `migrate`. Title/location resolution lives in **`_event_content`**, shared by `build_invite_calendar`, `_subject_title` and the fingerprint — resolving it twice is how a "no change" fingerprint drifts from the mail actually sent. Surfaced as `invite_stale` in `_shift_invite_flags`/`_shift_to_dict` and on grid chips as `.shift-chip--invite-stale` (warning-toned; declared *after* `--invited` so it wins the ring). **`window.offerInviteResend(shift, done)`** (in **`app.js`**, so planning.js and edit_shift_modal.js share one copy) prompts on a save that returned `invite_stale` (and on drag-move) and POSTs `calendar_sync:invite-shift`; the modal partial carries `data-shift-invite-url` so it can find the endpoint, and `_shift_invite_flags` ships `invite_recipients` so the dialog names who is about to be mailed. The prompt is a **custom modal** (`#inviteResendModal`, bundled at the bottom of `_edit_shift_modal.html` so all four include sites get it), which means it must not stack on the shift modal still animating out — `whenModalsClosed()` waits for one close, then **falls back to `window.confirm`** if something is *still* open (the approve flows re-show their parent) rather than rendering a dialog trapped behind the backdrop. `done` fires exactly once however it ends — button, X, Esc or backdrop.
- **Failed invites** (`ShiftInvite.delivered_at`/`send_failed_at`/`send_error`): sends are **queued**, so "dispatched" is not "delivered" — a message the mail host rejects (bad address, rate limit) used to leave the shift wearing an "invite sent" chip *and* be skipped by every later sweep. The queue handler now writes the outcome back at the single choke point (`calendar_sync.tasks.run_send_invite_mail` → `invites.mark_send_ok`/`mark_send_failed`, then re-raises so the row still shows Failed with the SMTP error). Three rules hold it together. (1) **`_dispatch` saves the invite *before* enqueuing** — the handler updates that row, and a later full `save()` of the in-memory copy would overwrite the outcome with pre-send values (instantly under `SCHEDULER_TASK_EAGER`, and in production whenever the loop claims the task mid-request). (2) `mark_send_failed` **restores `prev_content_key`** (carried in the payload, guarded by a compare against the key that attempt sent, so a newer dispatch isn't clobbered) — a failed *update* must read as out-of-date, not as if the recipients hold the new times. (3) **`delivered_at` is the "does anyone hold this?" flag**, which is why migration `0005` backfills it from `sent_at`: left null, every pre-existing invite would look never-delivered. It decides both branches — `resync` bumps **SEQUENCE only when something was delivered** (a retry of a never-sent invite must not headline as "Update:"), and `clear_send_failure` **deletes** a never-delivered invite (nobody holds it → the shift is plainly un-invited and the sweep re-sends it) while a delivered one only loses its failure marks and falls back to stale. `invites.needs_send()` (stale **or** failed) is what `SendInvitesView` and `invite_pending_count` key on. Surfaced as `invite_failed`/`invite_error`/`invite_delivered` and on chips as `.shift-chip--invite-failed`, danger-toned, declared after `--invite-stale` so it wins; the shift modal shows the mail server's own words plus a link to the Jobs queue, and its button reads **Retry now**. Dismissal is the queue's **Clear failed** button via the `on_clear` hook (see the scheduler convention) — there is deliberately no separate "dismiss" control on the shift. **A failed CANCEL is the one case with no shift-side control at all**: deleting a shift is unconditional (it never depends on mail getting through, and the shift never comes back), so the invitee is left holding an event for a shift that no longer exists with no chip, modal or sweep able to reach it — the queue row's **Retry** is the entire remedy, which is why that button has to live on the row rather than on the shift. Tests: `apps/calendar_sync/tests/test_invite_failure.py`.
- **Mail circuit breaker** (`core.mail.require_sendable`/`blocked_reason`/`failure_streak`, `MailPaused`): one press of Send invites can queue thirty messages, and a refusal is rarely about the individual message — a rate limit, a dead host or a bad password refuses the next twenty-nine too, and hammering a server that just said no is how an account gets throttled harder. It is a **per-connection, all-mail** policy, not a calendar one: **every scheduler task that sends mail opens with `mail.require_sendable(role, payload.get("queued_at"))`**, which raises `MailPaused` (reason as its message) instead of connecting. The task's ordinary failure path then does the rest — for invites that means the shift is marked failed exactly as a real refusal would, so a skipped batch clears and re-sends in one press each. Deliberately **not** built into the scheduler: `scheduler/` knows nothing about mail and stays that way; its only contribution is that **`enqueue` stamps `queued_at` into every payload** (handlers see the payload, never the row). Two rules make it work. The streak is **derived from `EmailLog`** (the newest `FAILURE_STREAK_LIMIT`=3 rows for that `connection_name` all failed) rather than kept as a counter — it can't drift, and any success, including a diagnostic test after fixing the config, breaks it with **no reset step to remember**. And a message queued **after** the newest failure is always let through: only a success breaks a streak, so blocking everything would also block the retry that could clear it — that message is a deliberate probe, and it either clears the streak or renews it. Tests: `core.tests.test_email_settings.FailureStreakTests` + the breaker section of `test_invite_failure.py` (which drives the **real** backend with SMTP refusing, since faking the log rows would test nothing).
- **Invite subject lines follow SEQUENCE**: first send `Invitation:`, any re-send (resync / reconciliation, both of which bump `sequence` *before* `_dispatch`) `Update:`, withdrawal `Cancelled:`. A re-send lands next to the original in the recipient's inbox, so it has to read as an update to that shift rather than a second invitation to it. Declining is safe by design: the chip keeps the marker, and **`SendInvitesView` resyncs stale in-scope invites** (returning `resent` alongside `activated`), so the month's button picks up what the prompt was declined for. Two consequences to know: `reconcile.sync_invite`'s "failed" count no longer reflects *send* failures (those live on the task rows / `EmailLog` now — state changes are still counted); and `SendInvitesView` warns (on the reload it triggers) when `SchedulerHeartbeat.is_alive()` is false, or the invites sit unsent. The **"Send myself a test invite"** button (`InviteTestView`) is the one exception that still sends *inline* — it enqueues a single `calendar.test_invite` task whose handler runs `send_test_invite` (REQUEST + immediate back-to-back CANCEL via `_send_mail_now`, so it can report a live pass/fail onto the "Last test" badge); the view **fails fast** if calendar mail isn't configured. Tests that assert an invite send set **`@override_settings(SCHEDULER_TASK_EAGER=True)`** so `enqueue` runs the task inline (see the scheduler convention). See the scheduler convention.
- **A shift chip's colour says *whose* job, its border style says *whether it's settled*.** One channel each: `_shift_chip.html` hands the workplace's colour to the CSS as an inline **`--wp-accent`** (accent, else `color`) on *both* branches, and `.shift-chip` derives `--chip-accent: var(--wp-accent, var(--primary))` from it, which drives the approved chip's fill+border and the planned chip's dashed border alike. Approved chips used to be painted in the app accent regardless, so approving a shift silently changed which employer it looked like it belonged to. The approved tint stays deliberately quiet (8%/20%, and 42%/85% in dark mode where a low tint vanishes on a sunk cell) so solid-vs-dashed still reads as the state. `planning.js`'s `buildShiftChip` sets the same property (never `style.borderColor`) — it inserts chips without a reload.
- **Shift chips are width-starved, so a new indicator needs a plan.** A full chip (avatar 16px + times + hours + break cup + 14px type band + the hover pencil) wants ~175px and a month-grid day cell gives ~145px — that is how the pencil came to be drawn on top of the type band. Two rules follow. **Invite state is a ring, not an icon** (`.shift-chip--invited` / `--invite-stale` / `--invite-failed`): a `box-shadow` costs no width, and its wording rides in the chip's `title` instead. It has to survive the amber overlap marker, which is an `outline` — different property, so both paint, but the ring's spread (2.5px) must exceed the outline's 1px or the amber covers it, and overlapping shifts are exactly the ones being read closely. And **anything pinned to the chip's right edge must clear the band** — `.shift-chip:has(.shift-chip__type)` shifts the pencil and the approved tick to `right: 17px`. Chip `margin-bottom` is **4px**, not 1px, because rings take no layout space and two stacked chips' rings otherwise touch. Marks are **planned-only** where they answer a planning question (see the invite-marker note in `_shift_chip.html`).
- **Shift type is picked with a swatch dropdown, not a bare select** (`window.initShiftTypePickers` / `.type-picker` in `app.js` + `style.css`): a native `<select>` can't colour its options, so the field read as plain words while the calendar spoke in colour bands and symbols. The template ships a working `<select data-type-picker>` and app.js *replaces* it — progressive enhancement, so a JS failure leaves a usable field — building the rows from the select's own `<option>`s (adding a type needs no edit there) and reusing `.shift-chip--type-*` / `.shift-chip__sym` so the modal can't drift from the chip. The select stays the value holder, so `.value` **reads** are unchanged; **writes must use `window.setShiftType(el, value)`**, never `el.value = …`, because assigning to a select fires no event and the visible button would keep showing the old type — the same rule as `setTimeValue`.
- **One shift modal** for the whole app: `assets/templates/_edit_shift_modal.html`, included by the planning calendar, the dashboard and the Approve Shifts page (`{% include … with title= icon= save_label= %}`). Its extras (workplace banner, fast-create warning, approved banner, overlap notice, delete button) ship hidden; whoever drives it reveals what it needs. The planning page drives it with `planning.js` (create + edit + approved sessions, so it keeps its own handlers); the approve flows use `js/edit_shift_modal.js` — `initEditShiftModal({onSaved, onDeleted, present, onHidden})`, where `present` lets a caller step a parent modal aside first. It validates end > start live (red inputs + disabled Save) rather than waiting for the server's 400. **Element IDs are the contract** between the partial and both scripts (`shiftModal`, `shiftForm`, `shiftStart`, …) — renaming one means touching both.
- The dashboard **Review & Approve** modal (`dashboard.js`) holds inline start/end/type edits **and** the row selection that only reach the server on **Approve Selected**, so it guards `hide.bs.modal` (+ `beforeunload`) with a discard prompt once anything is touched *or* selected (`dirty || anySelected()`; a reload we asked for ourselves sets `leaving`), and blocks Approve while a selected row's times are impossible. Opening the pencil modal passes the row's live field values as `prefill` (`rowValues()`), so unsaved inline edits carry over instead of being reverted to the server's copy. Refresh a single row with `updateRow()` after a pencil-modal save — a full `renderBody()` would rebuild the table from `SHIFTS` and wipe every other row's unsaved edits. Clicking a row's dead space latches a `row-focused` shade (accent-tinted, a step darker than the hover) as a place-keeping marker — it is **not** the selection, and clicks on a field/checkbox/pencil don't move it.
- Bootstrap's `.is-invalid`/`.is-valid` paint their own background icon and out-specify `.time-24-input`; `style.css` re-pins the clock glyph for those states (see `initTimePickers`).
- Some templates contain mojibake bytes (`â•Ð…`) in section comments. `replace_string_in_file` may fail to match those lines — use a small Python script with explicit `\u00e2\u2022\u0090` escapes when needed.
- **Never save a template with a UTF-8 BOM.** A BOM is a rendered zero-width character, not collapsible whitespace, so in an `{% include %}`d partial it emits an anonymous line box — one stray BOM atop `_calendar_component.html` put a phantom 24px gap above every calendar. (`{% extends %}` templates get away with it: their pre-block content is discarded.) Check with `p.read_bytes().startswith(b"ï»¿")`.
- **Django `{# … #}` comments are single-line ONLY — they do NOT span lines.** A `{# …` whose `#}` is on a *later* line does not close: everything up to the next `#}` is treated as literal text and **leaks onto the rendered page**. This mistake recurs almost every session — before writing any `{# #}`, confirm the `#}` is on the *same* line. For anything multi-line (or that you might later wrap), use `{% comment %}…{% endcomment %}`. Quick audit of a template: `grep -nE '\{#' file.html | grep -v '#}'` must return nothing.
- **Help system** (`apps/help/`): articles are DB rows (`HelpArticle`, Markdown in `body_md`, cached render in `body_html` refreshed on `save()` via `services.render_markdown` — **rendered on-server, no external calls**; templates print it with `|safe` because the editor is **staff-gated/trusted**). The manage table has a **Last changed** column plus **client-side** tools (all in `help.js`, guarded by `[data-help-manage]`): a global search box, per-column **funnel dropdowns** with searchable multi-select checkboxes (Pages/Keywords/Status; funnel turns `bi-funnel-fill`/accent when active), and single-active column **sort** (asc → desc → off) driven off `data-*` row attributes. Only **purge**/empty-trash calls the real `.delete()` (which cascades revisions); `export_articles` skips trashed rows, and `import_articles` sets `archived_at=None` so re-importing a shipped article also restores it. Page-awareness: `HelpPage` rows (synced from `services.HELP_PAGE_CONTEXTS`, keyed by URL **view-name**) are checkbox-assigned to articles; the popup fetches `help:context?page=<view_name>` using `{{ request.resolver_match.view_name }}`. Search is **client-side** over `help:search-index` JSON (title>keywords>summary>body ranking) in `assets/static/js/help.js`, which also drives: the offcanvas popup (opened by **F1** and a fixed gradient **`.help-fab`**, not a navbar icon — it opens **above modals** by raising z-index and pausing an open modal's Bootstrap focus-trap; a **`[data-help-open="slug"]`** element *anywhere on the page* also opens it straight to that article — e.g. the onboarding Review "?" nudges — opening the panel first if shut, then loading once shown); and the editor's **live preview + formatting toolbar + `/` slash-command menu** (one command catalogue, inserts Markdown), **live slug** (auto-fills from the title only while the slug is empty/untouched), and an **unsaved-changes guard** (`data-help-cancel` links + `beforeunload`). `base.html` shows the FAB + popup when `help_enabled` and (the user is authenticated **or** an onboarding page is showing) — all onboarding steps have `core:onboarding-*` page contexts, `/help/` is exempt from both onboarding funnels in `core.middleware`, and the anonymous account/claim steps surface only `public` articles — but never on `minimal_chrome` pages (context processor `help.context_processors.help_status`, cached; cleared by `services.invalidate_caches`). ## Code style & hardening

How new code / changes should be written:

- Match the surrounding code's style; don't restyle or re-comment code you didn't change.
- Keep views thin — heavy logic goes in `<app>/services.py`.
- Money is `Decimal` (never float), shown via en-DK L10N / the `dk` filter (see Conventions).
- Date-versioned data (tax profiles, pay rates): pick the effective row with `core.utils.active_dated_row`; never mutate historical rows.
- Ship new logic with a test under `apps/<app>/tests/` (run with the `apps` label).
- No new dependencies without a real need.
- Parse user input via helpers, don't hand-roll — `core.utils.parse_danish_decimal` for locale numbers; `parse_int_param` / `parse_iso_date_param` / `parse_iso_time_param` for request params (return `None`/default instead of raising → views answer 400, not 500).
- Dates: use `timezone.localdate()` / `timezone.localtime()`, never `date.today()` / `datetime.now()` (`USE_TZ=True`; the server may not run in Danish time).
- Payroll month bounds: use `PayrollPeriodService.resolve_period_bounds(workplace, year, month)` → `(termset, start, end)`; don't re-derive the term-set/full-month fallback inline. Date-span overlap checks: `core.utils.date_spans_overlap`.
- **Salaried proration comes in a month form and a range form.** `active_day_split_range` / `covered_salary_range` / `salaried_period_lines` take arbitrary `(start, end)` dates; `active_day_split` / `covered_salary` / `salaried_month_lines` are thin calendar-month wrappers that delegate to them. Anything working in **payroll periods** (analytics) must use the range form — an offset period spans two calendar months, so the month form would prorate over the wrong span. New callers should prefer the range form and let the month wrappers stay for the dashboard/payslip paths that genuinely mean a calendar month.
- Sanitize uploads: SVGs go through `core.utils.sanitize_svg` — an XML **allowlist** parser that returns `None` for unparseable input (reject the upload). Both the customize view and data_io import enforce the shared icon constraints in `workplaces/services.py` (`ALLOWED_ICON_EXTS`, `MAX_ICON_SIZE`).
- CDN `<script>`/`<link>` tags are version-pinned **with SRI** (`integrity` + `crossorigin`) — keep the hash in sync when bumping a version (Google Fonts CSS is per-browser and can't have SRI).
- `data_io.perform_import` is `@transaction.atomic` and `full_clean`s imported rows (invalid shifts are skipped and counted; invalid term sets abort the import).
- Redirect only to same-origin URLs — follow the `_safe_next` pattern in `apps/core/views.py`.
- Use the ORM / Django forms (no raw SQL); rely on template auto-escaping — never `|safe` untrusted data.
- Keep secrets/config in env vars (see `bitgigs/settings/production.py`); never commit secrets. Don't weaken the production hardening there (HTTPS/HSTS/secure cookies, gated by `DJANGO_ENABLE_HTTPS`).

## Frontend bits

- Charts: Chart.js v4 from CDN; category x-axis with ISO date labels; stepped lines for rate history; segment dash for projected tail.
- Workplace icons: 256×256 PNG produced by Cropper.js; SVG uploads first go through `svgRecolorModal` (per-color or single-tint remap, hex + color-picker inputs, live preview) before being passed to the cropper.
- **Hiding with the `hidden` attribute is safe** — but only because `style.css` re-asserts `[hidden] { display: none !important }`. Bootstrap's own display utilities (`.d-flex`, `.d-block`, …) are `!important` at the same specificity as reboot's `[hidden]` and come later in its bundle, so without that rule `hidden` is silently ignored on any element carrying one (it once showed both scheduler liveness banners at once). Don't remove it, and don't work around it with `d-none` juggling.
- Auto-dismissing notices: add `data-dismiss-after="<ms>"` to any Bootstrap `.alert` and `initDismissibleNotices` (`app.js`) swaps the close button for a draining **countdown ring** (`.notice-timer`, CSS in `style.css`) that dismisses on empty; hovering pauses it and reveals a click-to-close X. `base.html` opts success messages in.
